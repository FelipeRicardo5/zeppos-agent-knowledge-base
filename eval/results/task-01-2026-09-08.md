thing a wearable SDK does — could not be done.

Of the 35 symbols the project touches, **15 carry no stated `API_LEVEL`**, so 43% of
the app's API surface is unverifiable against the Bip 6 or against any other device.

The artefact is a project-shaped honest failure: real code where the base supports
it, three `throw`-ing stub files where it names a dependency it does not carry, and
13 numbered `ASSUMPTION` markers inline where I had to invent. Nothing invented is
unmarked.

## 3. Gaps, ranked

### G00 — No symbol in the base carries a call signature *(root cause)*
- **What was missing:** for all 409 symbols, the parameters, return value, and — for
  the `value`-typed classes — the instance members. Verified against the source of
  truth: every record in `data/symbols/*.json` has exactly eleven keys, and none of
  them describes the call.
- **Where it should have lived:** a `signature` / `params` / `returns` / `members`
  field on the symbol record, surfaced as a row in each `api/<module>.md` table or a
  fenced block under each description.
- **What it cost:** it is the direct cause of G01, G06, G11, G12, G13 and G14 — six
  of the seven worst gaps below. The base answers *may I use this symbol* completely
  and *how do I use this symbol* never. For "does this run on a Bip 6" that is
  sufficient. For "produce real code, not pseudocode" it is the whole task.
- **Workaround:** none available. Every call in the artefact is either copied out of
  a pattern snippet or labelled as invented.
- **Note:** `SKILL.md` discloses a *narrow* version of this ("Methods reached through
  a returned object… are not recorded. Their parent function is") which reads as a
  minor edge case about `DownloadTask.cancel`. It is not an edge case. It is the
  shape of the entire base, and a reader of `SKILL.md` will not learn that.

### G01 — Nothing about how to read a heart rate *(blocked the task's headline feature)*
- **What was missing:** the constructor form of `@zos/sensor.HeartRate`, any member
  that returns a bpm value, any subscription for "as it changes", the units, the
  range, and the sentinel for "no reading yet". Four facts are recorded: it exists,
  its type is `value`, its minimum is 2, its permission code is
  `data:user.hd.heart_rate`.
- **Where it should have lived:** `api/zos-sensor.md`, under
  `### @zos/sensor.HeartRate` — and, better, as a `patterns/` page. Sensor reading is
  the most common Zepp OS task and 0 of the 11 patterns touch a sensor.
- **What it cost:** forced the largest single assumption in the artefact. A wrong
  guess here does not fail loudly — it ships plausible-looking wrong heart rates to
  a user's server.
- **Workaround:** confined the invention to `page/heart-rate.adapter.js` and made it
  probe for a reader at runtime, so a bad guess degrades to a visible failure rather
  than a silent one.

### G02 — `MessageBuilder` is named but not carried *(hard block)*
- **What was missing:** `shared/message.js`, `shared/message-side.js` and
  `shared/device-polyfill.js`. `patterns/bluetooth-communication.md` is the base's
  only device↔phone guide, its own prose says these three files are what the two
  halves "rely on", and the base carries none of them — not the source, not an API
  page, not a symbol. Also missing: what `appDevicePort: 20` / `appSidePort: 0` mean,
  the error contract (no snippet has a `.catch`), reconnect behaviour, and payload
  size limits.
- **Where it should have lived:** an `api/shared-message.md` page for the
  `MessageBuilder` surface (the 9 members the snippets exercise are already
  enumerable from the guide), plus a "this library is vendored from the ToDoList
  sample, get it from X" note on the pattern page.
- **What it cost:** blocked requirement 2 outright, and blocked G18's workaround with
  it — so it also blocks requirement 3 reaching the watch. Two of five requirements
  die here.
- **Workaround:** none. Wrote three `throw`-ing stubs documenting the block, rather
  than invent a binary BLE protocol.

### G03 — The Settings App has no entry point *(hard block)*
- **What was missing:** whatever registers a settings page. Zero hits for
  `AppSettingsPage` across `api/`, `runtimes/`, `patterns/`, `data/` and `skills/`.
  One hit for `Settings.render`, in `SKILL.md`, where it appears on the list of things
  *not extracted*.
- **Where it should have lived:** `api/settings-app.md` as a module, listed in
  `api/index.md` and `runtimes/settings.md` alongside the `ui` components it wraps.
- **What it cost:** blocked requirement 3. `setting/index.js` is the one file in the
  artefact whose *first executable line* is invented; it is the line a real build
  would fail on.
- **Workaround:** none. Wrote it with a header block enumerating exactly what is
  cited (component names, storage keys) and what is not (everything else).

### G12 — Not one prop of one Settings App component is recorded
- **What was missing:** props for all 13 `ui` components, the option-list shape for
  `Select`, the change-callback name, and the module's import path (it is named plain
  `ui`, not `@zos/ui`, and no path is given). 12 of the 13 have an **empty**
  description; only `View` says anything, and what it says is "analogous to the `div`
  in the Web standard".
- **Where it should have lived:** `api/ui.md`, per component. The two the task needs
  by name — `TextInput` and `Select` — are both in the empty-description group.
- **What it cost:** compounds G03. Even given an entry point, the screen could not be
  written.
- **Workaround:** none. Every prop in `setting/index.js` is marked invented.

### G14 — How to update a widget after creating it
- **What was missing:** the documented route from "I have a TEXT widget" to "it now
  shows a different number". `api/zos-ui.md` has `setProperty` ("Set the properties
  of the UI widget.") and `prop` (empty description, no members). The base's only
  `prop` member with evidence behind it is `prop.VISIBLE`, from
  `patterns/widget-group.md`; `prop.MORE` appears once, buried inside the *prose of
  `getProperty`'s description*, and only in the reading direction.
- **Where it should have lived:** members listed under `### @zos/ui.prop`, and a
  worked "update a widget" snippet in `patterns/`.
- **What it cost:** forced an assumption on requirement 1's "updating as it changes",
  the one behaviour that makes the screen live rather than static.
- **Workaround:** used `w.setProperty(prop.MORE, { text })`, marked A13.

### G13 — `setProperty`'s two incompatible forms
- **What was missing:** which one is real. `api/zos-ui.md` lists `setProperty` as a
  module symbol (`>= 2`, OFFICIAL), which reads as `import { setProperty }` then
  `setProperty(w, …)`. `patterns/widget-group.md` — the base's only executable
  evidence — calls `img_icon_widget.setProperty(prop.VISIBLE, false)`, an instance
  method with a different arity. Same for `getProperty`, whose own description says
  `widget.getProperty(prop.MORE, {})` while the API table lists it as a module symbol.
- **Where it should have lived:** the `type` column already exists on every row and
  could carry `method` as distinct from `function`. Roughly 20 `@zos/ui` rows look
  like instance methods filed as module symbols (`redraw`, `setAlpha`, `setEnable`,
  `getId`, `getType`, `addEventListener`, …).
- **What it cost:** wasted time, then a coin-flip. I got this wrong on the first pass
  and only caught it on reading `widget-group.md` — the eighth pattern I opened.
- **Workaround:** followed the executable code over the API table.

### G06 — `createWidget`'s second argument has three spellings
- **What was missing:** one canonical form. `patterns/code-organization.md` shows
  `createWidget(widget.TEXT, { attr: {...}, styles: TEXT_STYLE })`;
  `patterns/multi-screen-adaption.md` shows `createWidget(widget.TEXT, textStyle)`
  with style keys flat; and that same file's own square-screen branch nests
  `x/y/w/h` under `attrs` while its round branch keeps them top-level. All OFFICIAL.
- **Where it should have lived:** a signature on `### @zos/ui.createWidget` (G00).
  Failing that, a note on the pattern pages that upstream is inconsistent here.
- **What it cost:** forced an assumption on the single most-used call in any Zepp OS
  app. Both pattern pages are faithful to their sources, which is why the base cannot
  see the contradiction — it has no cross-pattern consistency check.
- **Workaround:** used the flat form (two occurrences vs one).

### G11 — `fetch` delegates its whole contract to MDN
- **What was missing:** the argument shape, whether it takes `(url, options)` or a
  single object, the response object's members, and — most importantly — *which parts
  of the web Fetch API the Zepp side runtime actually implements*. The description is
  a link to MDN.
- **Where it should have lived:** `api/fetch.md`, with the divergences from the web
  API called out. A pointer to MDN is exactly the "answer from your own knowledge"
  the task forbids.
- **What it cost:** forced requirement 2's actual HTTP call to be written from
  outside the base.
- **Workaround:** wrote the MDN single-object shape and labelled it A7.

### G18 — No documented path from the Settings App to the Device App
- **What was missing:** how the watch learns the endpoint the user typed on the
  phone. `settings-storage` is attributed to the Settings App and Side Service only;
  it does not appear in `runtimes/device-app.md`. Nothing states that the Device App
  cannot read it, nothing states how it should instead.
- **Where it should have lived:** a `patterns/app-settings.md` page. This is the
  single most common Mini Program data flow and the base has no page for it.
- **What it cost:** forced an architecture guess (Side Service listens, then pushes
  over the transport) that immediately re-entered the G02 block.
- **Workaround:** implemented the push route, both halves marked.

### G04 — The four UI namespaces carry no `API_LEVEL`
- **What was missing:** minimums for `@zos/ui.widget`, `.align`, `.text_style`,
  `.prop` (and `.event`) — all "not stated", all OBSERVED.
- **Where it should have lived:** `compatibility/zos-ui.md`. A derived floor would
  do: these are namespaces on a module whose `createWidget` is `>= 2`.
- **What it cost:** it quietly voids the base's headline compatibility claim. No UI
  code compiles without these four, so by the base's own rule — "Treat absence as
  absence of evidence" — **no Device App UI in this base can be certified for any
  device**, including the "353 of 353" Bip 6. 15 of the 35 symbols my project touches
  are in this position.
- **Workaround:** none. Recorded it and shipped the app unverifiable.

### G16 — The "29 symbols with no stated minimum" figure is wrong *(WRONG)*
- **What was missing:** an accurate count. `compatibility/devices.md` says the
  "Symbols available" column "is a floor: the 29 symbols with no stated minimum are
  excluded from every count", and `skills/zepp-os/SKILL.md` repeats it. Counting
  `data/symbols/*.json`: 409 total, 353 with a minimum, **56 without**. 353 + 29 =
  382, which is not 409 — the inconsistency is visible on the face of `api/index.md`.
- **Where it should have lived:** it is derived, so it should not be a hand-written
  number at all — `devices.md` and `SKILL.md` should both interpolate it from the
  data at render time.
- **What it cost:** trust. This is the one number the base offers as evidence that it
  is honest about its own incompleteness, and it understates that incompleteness by
  about half. It is also the only claim in the base I checked against the data and
  found false, which makes me wonder how many of the others I did not check.
- **Workaround:** counted it myself; used 56 throughout this report.

### G17 — 42 symbols have an empty description
- **What was missing:** descriptions for 42 of 409 records — including 15 in
  `@zos/ui` (`align`, `prop`, `widget`, `text_style`, `event`, `KEYBOARD`,

- **Where it should have lived:** an explicit `*No description in any source.*` line

- **What it cost:** wasted time re-reading `api/zos-ui.md` twice, convinced I had
  missed the section.

### G07 / G08 — `app.json` is half-covered, and the uncovered half is the part you need first

- **Where it should have lived:** an `app-json.md` reference page — three pattern

- **What it cost:** every project needs this file first, and the covered fragment
  (`targets`) sits inside a pattern about *adapting an existing app to new devices* —

- **Workaround:** cited `targets`, invented the rest, marked the file's header.
- **Note:** the task's own notes predicted `app.json` would be a total block. It is

### G05 — The entry-point globals are not symbols

- **Where it should have lived:** `api/zos-global.md` should say these are ambient

- **What it cost:** an assumption on the first line of three of the five source files.

### G15 — `localStorage` vs `LocalStorage` vs `localStorage-instance`
- **What was missing:** what `localStorage-instance` is. It is the only one of the
  three reachable at level 2, so it is exactly the symbol a Bip 5 answer turns on —
  and its name is not valid JavaScript, so it cannot be what a developer types. It
  looks like an extraction artefact (an upstream page documenting the *instance*
  members of `localStorage`) that has been promoted to a first-class symbol.
- **Where it should have lived:** folded into `localStorage` as its member list
  (which is also the fix for G00 on this module), or flagged as a doc-page artefact.
- **What it cost:** wasted time on the Bip 5 answer; I had to reason about whether a
  level-2 persistence route existed and conclude that the base offers one only
  nominally.
- **Workaround:** used `LocalStorage` (`>= 3`), which has working code behind it, and
  reported the Bip 5 as failing requirement 4 on that basis.

### G09 — The Side Service and Settings App are entirely level-free
- **What was missing:** any `API_LEVEL` for any of their 41 symbols.
- **What it cost:** zero, actually — and it is worth saying so. `SKILL.md` and
  `runtimes/index.md` both disclose it clearly and up front, so I never wasted a read
  on it. It is a known hole, well signposted, and the least damaging thing on this
  list. Compare G04, which is the *same* hole in the Device App, is not signposted
  anywhere, and silently voids the compatibility claim.

## 4. Structural notes

**1. `SKILL.md`'s order is right for the question it anticipates, and wrong for
building an app.** Its five steps assume the question is *may I use symbol X on
device Y*. For that, the order is perfect and I followed it: runtime, device, both
axes. But building went `SKILL.md` -> `runtimes/index.md` -> `devices.md` -> **straight
to `patterns/index.md`** and only then into `api/`. The patterns are the only place
with executable code, so they are where authoring starts, and `SKILL.md` files them
fourth, framed as a fallback for when "the question is a task rather than a symbol".
Writing an app is *always* a task. The step order should be: identify device →
find the pattern → then use `api/` and `compatibility/` to verify what the pattern
told you.

**2. Most-returned-to: `patterns/multi-screen-adaption.md` and
`patterns/code-organization.md`, four visits each** — not for their topics, but
because they are where the only real `createWidget`/style code lives. I was mining
guides about screen shape for basic authoring syntax. `api/zos-ui.md` I opened three
times and left empty-handed each time: it has 74 rows and no signatures, so it can
confirm a name exists but never help me type a call.

**Never opened:** `api/zos-alarm.md`, `zos-app-access.md`, `zos-crypto.md`,
`zos-i18n.md`, `zos-interaction.md`, `zos-media.md`, `zos-notification.md`,
`zos-router.md`, `zos-share-storage.md`, `zos-user.md`, `zos-fs.md`,
`runtimes/watchface.md`, `runtimes/workout-extension.md`, `patterns/i18n.md`
(skimmed), `patterns/widget-group.md` (opened late, and it turned out to hold the
answer to G13 — see note 4).

**3. `api/zos-settings.md` is the one page that actively pointed me the wrong way.**
Its facts are correct, but its *name* is the name of the thing I was looking for. In
a Mini Program, "settings" means the phone-side screen where the user configures the
app; `@zos/settings` is the device-side reader for *system* preferences — units,
language, date format. I opened it expecting the bridge for requirement 3 and read
all 23 symbols before accepting it was unrelated. Nothing on the page, in
`api/index.md`, or in `runtimes/device-app.md` warns of the collision, and the real
neighbour — `settings-storage` — sorts elsewhere in `api/`. One cross-reference line
on each page would fix it: *"For the Mini Program's own settings screen, see
`settings-storage` and `ui`."*

**4. The base has no cross-pattern consistency check, and that is where its worst
ambiguities live.** G06 and G13 are both cases of two pattern pages, each faithful to
its own upstream source, contradicting each other — and the base has no mechanism
that could notice. A pattern page carries a derived `Minimum API_LEVEL`, so the
machinery for cross-page derivation already exists; the same pass could flag when two
snippets call one symbol with different arities. As it stands, G13 was only caught
because I happened to open an eighth pattern page about an unrelated topic. Had I
stopped at seven, the artefact would have shipped the wrong `setProperty` form with a
confident citation attached, which is a worse outcome than a marked gap.

**5. The confidence tier does not discriminate, but it does hide a real signal.**
Step 5 of `SKILL.md` says "Prefer official docs and samples (confidence tier
`OFFICIAL`/`OBSERVED`) over anything inferred" — but the split is 385 OFFICIAL / 24
OBSERVED and nothing is inferred, so there is never a choice to make and the
instruction is inert. The interesting fact is underneath it: **all 24 OBSERVED
symbols have an empty description** — the tier is 100% name-only — and 18 OFFICIAL
symbols are undescribed too. So the field a reader actually needs is not "how good is
the source" but "what does this record contain": name only, described, or backed by a
worked example. An `evidence: name-only | described | worked-example` axis would
predict my experience of this base almost perfectly, and `OFFICIAL`/`OBSERVED`
predicts nothing. Worth noting that every `@zos/ui` namespace behind G04 and G14
(`widget`, `align`, `text_style`, `prop`, `event`) is OBSERVED and therefore in the
name-only group — the tier already marks them, it just does not say what the mark
means.

**6. What I would have searched for, if search existed.** Every one of these is a
question I answered by grep or by opening files on a hunch:
- **`"HeartRate" usage`** — full-text across pattern snippets, not just the symbol
  index. The `patterns/index.md` inverse index only lists symbols a guide *imports*,
  so a symbol used inside a snippet without an import is unfindable.
- **`app.json`** — the fragment that exists is buried in a pattern about a different
  topic; a text search finds it in one step, browsing the structure never does.
- **`AppSettingsPage`, `AppSideService`, `Settings.render`** — I needed to prove a
  *negative*, and grep is the only tool in the base that can. This is the most
  important search case and the structure offers nothing for it: there is no "things
  we know exist but have not extracted" list. `SKILL.md`'s "What absence means here"
  section is prose; it should be a manifest.
- **`setProperty`** — to find every place a symbol is *called*, not just declared,
  which is how G13 surfaced.
- **`"Bip 6"` -> its `targets` slug** — a device-name lookup across `devices.md` and
  the pattern examples simultaneously.

A symbol-to-snippet index (the inverse of what `patterns/index.md` already builds,
extended from imports to call sites) would have collapsed roughly a third of my file
reads.

## 5. Trust check

### Three claims in the code the base supports

1. **The Bip 6 reaches `API_LEVEL` 4.2, so every `>= 2`/`>= 3` symbol in this project
   is available on it.** `compatibility/devices.md` — "Amazfit Bip 6 | 4.2 | 5.0 |
   353 of 353 | square, 390 x 450 | 2 | yes | 9765120*, 9765121, 10158337".
   The only symbol I use above 2.1 is `@zos/storage.LocalStorage` at `>= 3`
   (`compatibility/zos-storage.md`, "## API_LEVEL 3") — comfortably reached.

2. **The HTTP request must happen in the Side Service, not on the watch.**
   `runtimes/side-service.md` lists `fetch.fetch`; `runtimes/device-app.md` does not,
   across all 31 of its modules. `api/fetch.md` corroborates: "The use of `fetch()`
   in the *Side Service*…". This is what drove the whole architecture, and it is the
   base carrying real design weight, not just a lookup.

3. **`LocalStorage`'s `getItem`/`setItem` are the right persistence calls, and
   writing in `onDestroy` is the sanctioned shape.** `patterns/persistence-storage.md`
   ships the working code — `new LocalStorage()`, `localStorage.getItem('state')` in
   `build()`, `localStorage.setItem('state', …)` in `onDestroy()` — and
   `api/zos-storage.md` confirms the semantics ("data cleared after Mini Program
   uninstallation"), which is what requirement 4 needs. `page/index.js` follows it
   exactly. This is the one requirement I would defend in review.

Two more worth crediting: the 64 px square-screen status bar
(`patterns/multi-screen-adaption.md`) that sets my layout origin, and the
`try/catch` + stack-splitting recipe in `build()` (`patterns/error-catch.md`),
both lifted directly with no invention.

### Three claims in the code the base does **not** support

1. **`new HeartRate()` has a member that returns the current bpm, and a callback that
   fires when it changes.** Invented outright. The base records four facts about
   `HeartRate` and none of them is an API. `page/heart-rate.adapter.js` probes five
   candidate reader names and three candidate subscriber names at runtime and falls
   back to `setInterval` polling — which is engineering around my own ignorance, not
   knowledge. **This is the most dangerous line in the artefact**, because a wrong
   guess here produces a screen that looks like it works and a stream of wrong
   numbers arriving at the user's endpoint. If one gap gets fixed from this run, it
   is this one.

2. **`AppSettingsPage({ build() { return View({...}, [...]) } })` is how a settings
   screen is registered, and `TextInput`/`Select` take `label`/`value`/`options`/
   `onChange`.** Invented in full — entry point, import path, calling convention, and
   every prop. The base gives me 13 component *names* and one sentence about `View`.
   `setting/index.js` carries a header block saying so. It would fail on its first
   executable line.

3. **`w.setProperty(prop.MORE, { text })` updates a TEXT widget's text.** Half
   invented, and the honest accounting matters: `setProperty` as an instance method is
   cited (`patterns/widget-group.md`), and `prop.MORE` exists (buried in
   `getProperty`'s description) — but `prop.MORE` carrying a `{ text }` payload
   *inbound* has no evidence anywhere. The base's only demonstrated write is
   `prop.VISIBLE`, a boolean. So requirement 1's "updating as it changes" rests on a
   guess.

**And three smaller ones, for completeness:** the `fetch({ url, method, headers,
body })` object shape (G11 — taken from MDN, i.e. from outside the base); the
`app.json` skeleton around the cited `targets` block, including `"bip-6"` as the
target slug and `permissions` as the home for `data:user.hd.heart_rate` (G07/G08);
and `settingsStorage` being reachable as a bare global in both phone-side runtimes
(G10 — `api/settings-storage.md`'s own text writes it `settings.settingsStorage.length`,
hinting at a `settings` object the base never documents).

## What this run says about the base, in one paragraph

The knowledge base is excellent at the question it was built for and was not built
for the question in this task. *May I use symbol X on device Y* is answered
completely, quickly, and with better structure than the upstream docs — requirement
5 fell out of a single file read, and the Side-Service-owns-`fetch` insight that
shaped the whole architecture came from one more. *How do I call symbol X* is not
answered anywhere, for any of 409 symbols, and the eleven pattern pages are the only
executable code in the base — which makes them load-bearing far beyond their eleven
topics, and means their mutual contradictions (G06, G13) are unpoliced. The two gaps
this task predicted are both real but both smaller than advertised: the phone-side
level-free zone (G09) is disclosed so well it cost me nothing, and `app.json` (G08)
turns out to be half-covered. The two that actually stopped the work were not
predicted: **no symbol carries a signature (G00)**, and **the most-used UI namespaces
carry no `API_LEVEL` (G04)**, the second of which quietly voids the "353 of 353"
claim the base makes about the very device this task targets.
