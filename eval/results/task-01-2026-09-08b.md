## 1. Verdict

**Finished, with the Settings App built on sand.** All five files exist, are
syntactically valid, and every API call carries a citation or an explicit
`[ASSUMPTION #n]` marker. Nothing blocked me outright.

**Would I ship it? No — not without a toolchain.** Three specific reasons, in order:

1. **`setting/index.js` is largely invention.** The knowledge base contains *one line*
   of Settings App code across all 33 sample apps. The entry point, the import
   specifier, and every component prop are guesses. This is a required feature of the
   task, and I could not do better than a shape that looks plausible.
2. **The HTTP POST is a guess in its details.** `this.fetch({ method, url })` is
   attested for a GET. Adding `headers` and `body` is not.
3. **Nothing was executed.** I have no toolchain, no simulator, and no device. "Valid
   JavaScript" is the only claim I can make about the code, and I checked exactly that
   with a parser — nothing more.

What I would ship *today* is the Device App page and the Side Service's request
routing. Those rest on verbatim sample code from the 3.0/4.0 samples and I have
reasonable confidence in them, with the one exception of `HeartRate.getCurrent()`.

The base carried a real share of the work — the device compatibility question, the
sensor's existence and permission code, persistence, screen adaptation, logging and
the whole Side Service skeleton were answered directly and well. It failed almost
exactly at the boundaries between runtimes: the phone side of a three-runtime app.

## 3. Gaps, ranked

### G1 — The Settings App has no usable record at all
*Cost: forced assumption across an entire required feature; the single worst gap.*

**What was missing:** the entry-point function that registers a settings page; the
import specifier for the 13 `ui.*` components; the props of every one of them; and the
option shape for `Select`. Twelve of the thirteen components have no description —
only `ui.View` has one sentence.

**Where it should have lived:** `api/ui.md` should carry per-component prop tables
(the upstream source is one `.mdx` per component — `data/symbols/ui.json` records
`app-settings-api/ui/select.mdx` — so the material exists and the extractor dropped
everything but the name). The entry point needs a record in `runtimes/settings.md`.
Most cheaply of all: `examples/application-4-0-todo-list.md` and
`application-2-0-post-health-data-miniprogram.md` both list a **Settings App** file
under "Files" and then show **zero** excerpts from it — the example extractor only
follows `import` statements, and Settings App files evidently do not import in a way
it recognises. Fixing that one blind spot would populate this gap from code that is
already in the corpus.

**How I worked around it:** built the file around the one attested line
(`props.settingsStorage.getItem(...)`), used only component names the base vouches for,
and marked every prop `[ASSUMPTION #9a–g]` at the call site.

### G2 — `fetch` has no request shape beyond a bare GET
*Cost: forced assumption on requirement 2.*

**What was missing:** how to pass a request body, headers, or a method other than
`get`; and what the resolved value contains (status? a parsed body?).

**Where it should have lived:** `api/fetch.md`. Its description currently *delegates*
— "can be found in Fetch API - MDN" — which is a pointer out of the base, and the base
elsewhere insists on not answering from outside itself. Alternatively:
`examples/application-4-0-fetch-api.md` is the sample named for this API and shows no
`fetch` call at all (see G3's sibling problem, row 16).

**How I worked around it:** used the attested `{ method, url }` and added
`{ headers, body }` on MDN's naming, marked `[ASSUMPTION #8]`.

### G3 — The zml page→side request call is absent
*Cost: forced assumption; the entire watch↔phone link depends on it.*

**What was missing:** `this.request(...)` on a `BasePage`. The base records the
*receiving* half in three separate 3.0/4.0 samples and never the *sending* half.
Only the reverse direction is attested (`this.call({ type })`, side→device).

**Where it should have lived:** `api/zeppos-zml-base-page.md` — which currently
contains one table row and nothing else. Or `patterns/`: there is a pattern for
Bluetooth communication, but it documents the *superseded* MessageBuilder library,
not zml. A "Device App ↔ Side Service messaging (zml)" pattern is the missing page.

**How I worked around it:** composed the caller shape from
`patterns/bluetooth-communication.md` (`.request({method, params})` → promise) with the
receiver shape from `examples/application-4-0-todo-list.md`. Marked `[ASSUMPTION #5]`.

### G4 — `HeartRate` has no accessor and no change callback
*Cost: forced assumption on requirement 1.*

**What was missing:** any method on a sensor instance for heart rate, and any
push/subscription API for any sensor.

**Where it should have lived:** `api/zos-sensor.md` per-symbol descriptions, or a new
"Methods on a returned instance" section. `SKILL.md` already declares this class of
gap ("Methods reached through a returned object are not recorded") which is honest,
but for the sensor module it removes essentially all usability: every sensor here is
`type: value`, meaning you construct it and then need methods that are not recorded.
The `examples/index.md` "Methods called on a value" index *did* catch
`Calorie.getCurrent()` — so the mechanism works; it just found nothing for `HeartRate`
because the showcase sample's HR page apparently calls it in a form the extractor missed.

**How I worked around it:** `getCurrent()` by cross-symbol analogy, and polling on
`setInterval` instead of a subscription. Marked `[ASSUMPTION #1, #4]`.

### G5 — `app.json` field *values* are nowhere
*Cost: forced assumptions; would fail at build, not runtime.*

**What was missing:** what `configVersion` is set to, what `runtime.apiVersion`
contains, the sub-keys of `app`, and — worst — the contents of `targets.<k>.module`,
i.e. how a page is registered. `examples/index.md` deliberately records only which
*keys* appear in how many samples. The one guide showing `module` elides its body as
`// ···`.

**Where it should have lived:** the base has no `app.json` reference page at all, and
`SKILL.md` says so up front. It should have one: `reference/app-json.md`. The upstream
file exists — `patterns/multi-screen-adaption.md` and
`patterns/code-adaptations-for-new-devices.md` both link to
`zeppos-docs/docs/reference/app-json.mdx` — it simply was not extracted.

**How I worked around it:** wrote plausible values and flagged all of them (`G7` in
`CITATIONS.md`).

### G6 — No `targets` key exists for any 4.x-era device
*Cost: forced assumption; blocks packaging for the actual target device.*

**What was missing:** the string that keys `targets` and `assets/` for a Bip 6. The
33 sample manifests are all 1.0–4.2-era but their target keys top out at
`320x380-amazfit-bip-5`. `compatibility/devices.md` gives me `deviceSource` values for
the Bip 6 but never says that `deviceSource` is what links a device row to an
`app.json` target — I only learned that by grepping into a patterns page.

**Where it should have lived:** a `targets key` column in `compatibility/devices.md`.
The page already has `deviceSource`; the key is the missing neighbour, and this is the
single highest-leverage column the base could add.

**How I worked around it:** invented `bip-6` with the three real `deviceSource` values.

### G7 — `@zos/timer` does not contain the general-purpose timer *(BURIED)*
*Cost: wasted time; no wrong output.*

**What was missing:** nothing, in the end — but the module named `@zos/timer` holds
only `createSysTimer` (>= 4, and its own description restricts it to app services) and
`stopTimer`. The timer a page actually uses is `setInterval`, filed under
`@zos/global`. I went to the obviously-named module first and had to back out.

**Where it should have lived:** a cross-reference on `api/zos-timer.md` — "for a
page-scoped timer see `@zos/global.setInterval`".

### G8 — `setInterval`: module import or ambient global? *(AMBIGUOUS)*
*Cost: forced assumption; would fail at build.*

The base files it under a module path `@zos/global` but shows no import line and no
sample call anywhere. The module's *name* argues for ambient; its *path form* argues
for an import. `examples/index.md` lists `.clearTimeout()` under "Methods called on a
value" with a receiver it could not resolve, which does not settle it either.

**Where it should have lived:** `api/zos-global.md` needs one line saying whether these
are imported. **How I worked around it:** wrote bare, documented the alternative inline.

### G9 — Two conflicting `createWidget` prop shapes *(AMBIGUOUS)*
*Cost: forced a judgement call.*

`patterns/code-organization.md` shows `createWidget(widget.TEXT, { attr: {text}, styles })`;
all eight sample pages show flat props. `SKILL.md` anticipates exactly this and tells
you to prefer the sample — which I did. Credit where due: the base predicted its own
inconsistency. It should still be annotated on the pattern page itself, where a reader
who never opens `SKILL.md` will hit it.

### G10 — `showToast` parameter key: `content` vs `text` *(AMBIGUOUS)*
*Cost: forced assumption; a wrong guess yields a blank toast.*

Both spellings appear in official samples (2.0 vs 4.0), and `api/zos-interaction.md`
gives no parameter list. Probably a genuine upstream rename, which is worth recording
as such: "`content` before 3.0, `text` from 3.0" would be a one-line fix.

### G11 — `localStorage-instance` >= 2 while `LocalStorage` >= 3 *(AMBIGUOUS)*
*Cost: wasted time; nearly changed my Bip 5 answer.*

`compatibility/zos-storage.md` lists an instance at a lower level than its class. If
that means "the instance API was available at 2 under an older spelling", it would
change the Bip 5 verdict. I could not tell, so I did not use it, and said so.

### G12 — No clock in the Side Service *(SILENT)*
*Cost: forced assumption.*

No time symbol at all is recorded for the Side Service runtime, and `@zos/sensor.Time`
(Device App) has no attested accessor beyond `new Time()`. Timestamping a health
reading is not an exotic requirement.

### G13 — `SKILL.md` understates its own coverage *(WRONG)*
*Cost: would have caused me to skip pages that exist.*

`SKILL.md`, "What absence means here", states:

> The Side Service and Settings App use globals (`fetch`, `settingsStorage`,
> `Settings.render`) that are not extracted yet ... Questions about those are outside
> what this KB can answer — answer from the official docs and say where the answer
> came from.

Two of those three **are** extracted, with OFFICIAL descriptions: `api/fetch.md` and
`api/settings-storage.md` (7 symbols, each described). `runtimes/side-service.md` lists
20 symbols across 10 modules, and `runtimes/settings.md` lists 21. Only
`Settings.render` is genuinely absent. Had I obeyed the instruction literally I would
have answered from outside the base — the exact failure the task forbids — on two
questions the base answers well. The sentence should be narrowed to the settings
*entry point* and the *component props* (G1), which are the real holes.

## 4. Structural notes

**Did I read in the order `SKILL.md` describes?** For the first four questions, yes,
and it worked: runtime → device → symbol → level is the right spine for a
compatibility question, and it answered the Bip 6 / Bip 5 question cleanly and fast.

After that the work wanted a different order. `SKILL.md`'s order is organised around
*"may I use symbol X here"*. Building an app is not that question. Roughly nothing I
needed after hour one was a symbol lookup; it was all **shape** — what the call looks
like, what the file looks like, what the manifest looks like. The order the work
actually wanted was:

1. `examples/index.md` — pick the closest whole sample and read it end to end.
2. That sample's page (`application-2-0-post-health-data-miniprogram.md` is
   HeartSync with a different sensor), then its modern siblings for the current idiom.
3. `patterns/` for the cross-cutting mechanics (persistence, screen adaptation,
   `app.json` targets, logging).
4. `api/` and `compatibility/` **last**, as a verification pass over a design already
   drafted — which is exactly what the citation exercise turned into.

`api/` was never where I started a question; it was where I finished one.

**Page I returned to most:** `examples/index.md`, by a wide margin — four separate
visits. Its "Methods called on a value" section did more work than any other single
piece of the base: `setProperty`, `getItem`/`setItem`, `getCurrent` and `fetch` all came
from there, and none of them appear anywhere else. Runner-up:
`compatibility/devices.md`.

**Pages I never opened:** `runtimes/watchface.md`, `runtimes/workout-extension.md`,
`patterns/cross-page-communications.md`, `patterns/error-catch.md`,
`patterns/widget-group.md`, ~20 `api/zos-*.md` module pages (alarm, ble, crypto,
display, fs, media, notification, router, share-storage, settings, user, …), most
`compatibility/zos-*.md` pages, and 29 of the 33 example pages. That is expected — a
single app touches a thin slice — but it means my sample of the base is narrow, and a
different app would surface a different set of gaps.

**Anything actively misleading?** Two things.

1. **`SKILL.md`, "Where `app.json` comes from"** sends you to `examples/index.md`.
   That page tells you which *keys* exist and which permissions are declared, which is
   real and useful — but the thing I actually needed, the nested shape of `targets`
   (`module` / `platforms[].deviceSource` / `designWidth`), is in
   `patterns/code-adaptations-for-new-devices.md`, a page whose title reads like a
   porting guide and which `SKILL.md` never connects to `app.json`. I found it by
   grepping for `deviceSource`. The facts on both pages are correct; the signpost
   points at the smaller half of the answer.
2. **`SKILL.md`'s coverage disclaimer** (G13) is wrong in the direction that costs
   most — it tells you to give up on questions the base can answer.

A third, milder one: `api/zos-timer.md` is named for a job it does not do (G7).

**A note on the base's honesty.** The single most valuable thing here is that
`SKILL.md` names its own worst gap before you hit it — the `not stated` /
`OBSERVED` status of `widget`/`prop`/`align`/`text_style`, and the fact that a device's
"353 of 353" count excludes them. That turned what would have been a false confident
claim ("verified for the Bip 6") into a correctly hedged one. Very few reference
corpora do that, and it is worth not regressing.

**What I would have searched for, if search existed.** Almost all my dead ends were
one query each:

- `onCurrentChange` / `getCurrent` — "what can I call on a sensor instance?"
- `this.request` — "how does a page talk to the side service?"
- `AppSettingsPage` OR `Settings.render` — "how does a settings file start?"
- `deviceSource` — the query that found `targets` (I ran this one by hand, and it worked).
- `"pages"` — "how do I register a page?"
- `setInterval` — needed a *symbol → module* lookup; I had the name and not the home.

The shape that would have saved the most time is not full-text search but a **global
symbol index**: one file mapping every symbol name to its module, level, runtimes, and
the example/pattern pages that contain it. The three indexes that exist
(`compatibility/index.md`, `runtimes/index.md`, `examples/index.md`'s symbol list) each
hold one axis of that and are keyed by module or by page, so answering "where does
`setInterval` live?" means reading three files. A reverse index, symbol-first, would
collapse most of my BURIED and several SILENT rows into single lookups. Second most
useful: a `targets key` column on `compatibility/devices.md` (G6).

### Three claims in the code the base supports

1. **`page/index.js`** — *"The heart rate sensor is `@zos/sensor.HeartRate`, it needs
   the `data:user.hd.heart_rate` permission, it requires API_LEVEL >= 2, and it is

   `api/zos-sensor.md` (symbol table row: value, >= 2, OFFICIAL; description: "HeartRate

   `examples/application-2-0-showcase.md`,
   `zeppos-samples/application/2.0/showcase/page/sensor/heart_rate.js` line 12.
   Two independent axes plus running code.

2. **`README.md`** — *"This app does not run on a Bip 5, because
   `@zos/storage.LocalStorage` requires API_LEVEL >= 3 and the Bip 5 reaches 2.1."*
   `api/zos-storage.md` and `compatibility/zos-storage.md` (LocalStorage >= 3);
   `compatibility/devices.md` line 43 (Amazfit Bip 5 — API_LEVEL 2.1). The base
   answered a device question directly, which is the thing it says it is for.

3. **`app-side/index.js`** — *"HTTP belongs in the Side Service, not the Device App,
   and the request is `this.fetch({ method, url })`."*
   `runtimes/side-service.md` lists module `fetch`; `runtimes/device-app.md` does not.
   Call shape verbatim from `examples/application-3-0-download.md`,
   `zeppos-samples/application/3.0/download/app-side/fetch-module.js` line 8. This is

### Three claims in the code the base does **not** support

1. **`setting/index.js` — the entire file's skeleton.** `AppSettingsPage({ build(props) })`,
   `import … from 'zeppos-settings-ui'`, and every prop on `TextInput`, `Select` and
   `Button`. The base gave me thirteen component *names*, one sentence of description
   across all of them, and one line of usage. The entry-point name I wrote contradicts
   the one `SKILL.md` mentions in passing, and the base offers nothing to break the tie.
   **If any single thing in this project is wrong, it is this file, and it is a required
   feature.**

2. **`page/index.js` — `this.state.hrSensor.getCurrent()` and the polling design.**
   `getCurrent()` is transplanted from `Calorie`. Nothing in the base says a `HeartRate`
   instance has that method, or any method. Worse for the requirement: the task asks
   for a display that updates *as the reading changes*, and I implemented a poll
   because no sensor in the base has a recorded change callback. If one exists upstream,
   my design is not just unverified but the wrong shape — a polling loop where an event
   subscription belongs.

3. **`app-side/index.js` — `headers` and `body` on `this.fetch`, plus
   `page/index.js` — `this.request({ method, params })`.** Grouped because they are the
   same failure: I had one end of each call and invented the other. The single attested
   `fetch` is a GET with exactly two keys; the resolved value's shape is unknown, so my
   `.then(result => ({ ok: true }))` does not actually check that the server accepted
   anything. And `this.request` is a name that appears nowhere in the base at all —
   I assembled it from a superseded library's method plus a handler signature.
   **Requirement 2 ("sends each reading to an HTTP endpoint") is therefore not
   verifiable from this knowledge base, only plausible.**
