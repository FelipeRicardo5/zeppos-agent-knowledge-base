3. Gaps, ranked

1. Device App → Side Service call mechanism is undocumented anywhere in this base. Missing: the call signature and contract of whatever this.call()/this.request() is on BasePage, and its receiving counterpart. api/zeppos-zml-base-page.md and api/zeppos-zml-base-side.md are name-only (OBSERVED, no Methods section, no API_LEVEL). examples/index.md's two systematic indexes for unimported calls ("Methods called on a value" and "Global calls in the phone runtimes") — the exact mechanism this base uses to catch calls like .setProperty() — list neither .call() nor .request() nor onCall(), even though examples/application-3-0-download.md page/index.js shows the receiving half (onCall({ result })) and every Side Service sample shows onRequest(req, res). Where it should live: a Methods section on zeppos-zml-base-page.md/zeppos-zml-base-side.md, or a "Cross-Runtime Communication" pattern page. Cost: forced the single biggest unverified assumption in the shipped code — the entire Device→Side data path rests on it. Workaround: wrote this.request({method, params}) mirroring the req.method shape samples do show on the receiving side, flagged inline as unverified.

1. fetch and settingsLib/settings-storage carry no stated permission or API_LEVEL anywhere. Missing: whether posting to an arbitrary URL from the Side Service needs a permission string at all. runtimes/side-service.md states plainly "0 of 20 symbols" state a permission, and manifest/index.md's permission table has no row for fetch. Where it should live: a Requires in app.json line on api/fetch.md, matching the pattern every Device App symbol follows. Cost: shipped HeartSync with no permission entry for the one API the whole feature depends on — a real risk of the "install then die at runtime" failure mode SKILL.md itself warns about. Workaround: none available; documented the omission instead of inventing a permission string.

1. No worked example anywhere maps an API_LEVEL number to a runtime.apiVersion semver string. Missing: what "target"/"compatible"/"minVersion" should read for, say, "supports 2.1 through 4.2." The only complete app.json in this base (manifest/index.md's worked example) is 1.0-era ("1.0.0"/"1.0.1"), and I grepped every one of the 33 sample pages in examples/ for apiVersion — zero hits. Where it should live: a table on manifest/runtime.md joining API_LEVEL to apiVersion strings, or at minimum one modern worked example. Cost: forced a guessed value in app.json I have no way to verify against this base. Workaround: wrote 2.1.0/4.2.0/2.1.0 by analogy with the one example's shape.

1. runtimes/device-app.md never attributes hmUI to the Device App, but a shipped Device App sample uses it freely, and conflicts/index.md never lists the contradiction. Missing: a stated boundary for whether hmUI.\* (the watchface-only global per SKILL.md) is also legal, unlevel-certified, syntax in a 3.0+ Device App. Where it should live: a row in conflicts/index.md next to the existing widget/GRADKIENT_POLYLINE entries, which are exactly this shape of problem. Cost: wasted a genuine research cycle cross-checking two idioms before picking the more conservative one. Workaround: used the imported @zos/ui form, which is what the one sample built for a real Bip device uses.

1. v3's st/sr selector cannot target "the Bip 6" — only its whole screen-width class. Missing: nothing, really — compatibility/devices.md states this plainly ("Selects a screen shape and width, so a whole class of device"). It's a task-framing trap more than a base gap: a request to "target the Bip 6 specifically" naturally reaches for the newer v3 mechanism, which can't do that at all. Cost: would have silently over-targeted (Active, Cheetah Square, GTS 4, Bip Max all share s/w390) if I hadn't cross-checked. Workaround: used v2/deviceSource, listing Bip 6's and Bip 5's numeric IDs explicitly.

1. ui.Select has no settingsKey prop, unlike TextInput/Toggle/Slider, and the asymmetry is never explained. Missing: whether this is deliberate (Select genuinely can't self-persist) or a documentation gap. Where it should live: a note on api/ui.md's Select entry. Cost: minor — a few minutes double-checking the table before wiring persistence by hand. Workaround: manual onChange → settingsStorage.setItem.

1. Structural notes

- Order: mostly SKILL.md's build order (examples → manifest → patterns → api/compatibility-as-verification), but permission lookups (api/zos-sensor.md, api/zos-device.md) got pulled in while drafting app.json, not strictly last — building an accurate manifest needs permission facts before the "verification pass" step says to go get them. I'd suggest SKILL.md say that explicitly rather than implying a clean sequential pass.
- Most-returned-to: api/zos-ui.md (checked widget, align, prop, TEXT, BUTTON, Select at different points) and examples/application-2-0-post-health-data-miniprogram.md (the one sample that's both a full 3-runtime app and explicitly targets a Bip device — a rare, valuable combination).
- Never opened: runtimes/workout-extension.md, most of patterns/_.md beyond index.md and persistence-storage.md (not relevant to this task), annotations/, data/_.json (never needed to disambiguate a Markdown page), and hmSensor.id.md/hmSetting.md/hmBle.md/hmFS.md (watchface-only, not this app).
- Actively misleading: runtimes/device-app.md's silence on hmUI reads as "not available here," and nothing nearby warns that a shipped Device App sample contradicts that — see gap #4.
- What I'd have searched for if search existed: a cross-reference index from "task verb" (send, persist, communicate-between-runtimes) to symbols — patterns/index.md does this for on-device tasks but has no entry for "Device App talks to Side Service," which is arguably the single most common Mini Program task shape.

5. Trust check

Three claims the base directly supports:

1. HeartRate is Device App, >= 2, needs data:user.hd.heart_rate; onCurrentChange/offCurrentChange are each >= 2.1 — api/zos-sensor.md lines 23, 1040, 1053–1054; runtimes/device-app.md line 378.
2. Bip 6 reaches API_LEVEL 4.2, Bip 5 reaches 2.1 — compatibility/devices.md lines 27, 43.
3. ui.TextInput has a settingsKey prop that persists its value into Settings Storage — api/ui.md line 198.

Three claims I made that the base does not support:

1. That this.request({method, params}) returning a Promise is how page/index.js reaches app-side/index.js, and that onRequest(req, res) receives exactly that shape. This is the biggest single assumption in the code — see gap #1.
2. That shipping fetch() in the Side Service with no permission string in permissions is safe. The base is silent, not reassuring, on this — see gap #2.
3. That "apiVersion": {"compatible": "2.1.0", "target": "4.2.0", "minVersion": "2.1.0"} is the correct encoding of "2.1 through 4.2." No page anywhere states this mapping — see gap #3.
