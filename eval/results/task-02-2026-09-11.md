## 3. Gaps, ranked

1. **No documented shape for a Step sensor.** `hmSensor.id.STEP` is a bare enum name with no property table anywhere and no sample usage. Cost: the central assumption behind requirements 3 and 4. Should live: a *Called on a Step value* section on `api/hmSensor.md`, matching what `api/zos-sensor.md` already does for `@zos/sensor.Step`.
2. **Nothing connects `editable: 1` to any widget-level API.** The manifest flag and the `data_type` binding are real, separate facts. Cost: the central assumption behind requirement 5; cannot tell whether `IMG_POINTER`/`TEXT_IMG` are even the right widget kind.
3. **No lifecycle, and no way to unregister an `hmSensor` listener.** `runtimes/watchface.md` lists only `addEventListener`/`createSensor`/`id`. Cost: blocks full compliance with requirement 6 — only the poll timer can be gated.
4. **`SKILL.md` names a `WatchFace({...})` entry point the base cannot produce.** Found only in `SKILL.md`'s own prose. Cost: time chasing it, then a fallback to a 1.0-only shape.
5. **The official 3.0 sample blurs the `hm*`/`@zos/*` boundary `SKILL.md` declares absolute.** Cost: time resolving rule against sample; resolved by following the rule, losing logging. Should live: `conflicts/index.md`.
6. **`compatibility/devices.md` files GTR 3 Pro and GTS 3 as 1.0 with no `API_LEVEL`** while their own samples run `@zos/app.getScene` (>= 2). Cost: could not use the sample-precedented devices for requirement 7.
7. **`getScreenType()`'s values are never linked to the `screen_type` enum**, and that enum is app scene, not screen shape, despite the name. Cost: a few reads of confusion.
8. **No permission is documented for any `hm*` symbol**, so `permissions: []` is the only citable choice rather than a verified one.

## 4. Structural notes

- **Read order** followed `SKILL.md`'s building order, with one substitution: `runtimes/watchface.md` was front-loaded right after the first example, because the full symbol inventory was needed before any requirement could be matched to a candidate API.
- **`api/lookup.md` was used twice, narrowly.** Once the runtime was known to be watchface, the runtime-scoped pages were more direct. Its value is disambiguating an unknown owner, and that problem rarely arose here.
- **Most revisited:** `api/hmUI.widget.md`. **Never opened:** `runtimes/side-service.md`, `runtimes/settings.md`, most of `patterns/`.
- **Actively misleading: `patterns/multi-screen-adaption.md`.** It is the obvious page for "round vs square" and its facts are correct, but every symbol in it is Device App. Its position in `patterns/index.md` cost real time.

## 5. Runtime confusion check

- **Caught, not shipped:** the 3.0 timer sample's bare `getScene()` and `logger.log()`, matched to Device-App-namespaced records inside a watchface. Noticed while cross-checking the example JSON against `runtimes/watchface.md`. Neither symbol was carried into the code.
- **No `@zos/ui.*`, no `align`, no `import` anywhere in the project.** Every widget call is `hmUI.*`.
- **Where the base helped:** `runtimes/watchface.md`'s per-symbol *Also valid in* column made the overlap visible immediately.
- **Where it let the blur through:** it never flags the 3.0-timer contradiction itself.

## 6. Trust check

**Supported, with citations:** `ARC_PROGRESS`'s `level [0-100]`; `timer.createTimer(delay, period, callback, extra)`/`stopTimer(handle)`, verbatim in two example pages; `targets.*.module.watchface.editable` as the v3 location, documented and present in a real sample's `keyPaths`.

**Not supported:** that `hmSensor.id.STEP` exposes `.current`/`.target` — pure analogy, zero citation; that `editable: 1` lets the wearer repoint the `IMG_POINTER` widget — nothing connects the flag to any widget or callback; that `getScreenType() === AOD` stands in for "screen off" for battery purposes.

## Operator note, added 2026-09-11 after verifying the report

A report is evidence, not truth. Four claims were checked against the base
before this file was committed.

**Confirmed, and the first two are defects introduced by the session that built
the watchface front — written from memory rather than derived from the base, in
the file that forbids exactly that:**

1. **`SKILL.md` line 94** states `WatchFace({ ... })` "appears in code". It
   appears nowhere in `api/`, `data/`, `examples/` or any other output
   directory. The samples show `DeviceRuntimeCore.App({...})`.
2. **`SKILL.md` line 80** states a watchface "does not use `@zos/*`".
   `runtimes/watchface.md` lists `getScene`, `SCENE_AOD` and `log` as valid in
   watchface. The agent saw the contradiction, followed the prose over the data,
   and shipped without logging as a result.
3. **GTR 3 Pro and GTS 3** are indeed filed at `API_LEVEL` 1.0 with no stated
   level while the samples targeting them use `>= 2` symbols.

**Corrected — the report is right and the first triage of it was wrong.** Gap 3
was initially read as a discoverability failure, on the assumption that
`hmUI.widget.DELEGATE` answers requirement 6 and the agent simply did not find
it. It does not answer it, because the base does not hold the answer: the record
is `{ id: "hmUI.widget.DELEGATE" }` and nothing else. Its source page carries the
lifecycle callbacks in a table headed `| Callback Name | Description |`, a column
name in neither of the extractor's two column maps, so it was dropped in
silence. **Seventh bug of that class.** Requirement 6 is a coverage gap that this
base created, not one the agent failed to search for.

**Refuted, and it is the run's most valuable output.** Gap 1 — ranked first,
driving requirements 3 and 4 — says the base documents nothing about what
`hmSensor.id.STEP` returns. It does. `api/hmSensor.id.md` states `current` and
`target` with types and descriptions, and `api/lookup.md` points at that page in
one line. The agent's assumption was *exactly right* and the base could have
vouched for it.

It looked in `api/hmSensor.md`, `runtimes/watchface.md`,
`data/symbols/hmSensor.json` and `examples/index.md`. The answer is in
`api/hmSensor.id.md`, and **nothing on `api/hmSensor.md` points there**: that page
lists `id` as a bare constant, and the 18 sensor ids with their shapes are one
file away with no link. So requirements 3 and 4 should have been VOUCHED, and
the real finding is a navigation one — a module and its sub-module do not name
each other.

That also revises the report's own structural note. `api/lookup.md` was used
"twice, narrowly" and judged of little value here; the one question it would
have answered outright is the one the run ranked as the base's worst gap.

**A protocol defect the run exposed:** `prepare-run.ps1` strips `.git`, so the
agent cannot name the commit it measured — which section 0 of every task asks
for. The commit has to be given in the prompt.
